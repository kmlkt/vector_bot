## 1. Роли пользователей

| Роль | Кто | Как попадает |
|---|---|---|
| Ученик | 8–9 класс (в пилоте также 11 класс и 13–15 лет из секции) | `/start` → код класса + номер, или без класса |
| Учитель | классный руководитель / куратор пилота | `/start` → «Я учитель» → создает класс |
| Жюри | проверяющие | тестовый ученик с историей + тестовый учитель с классом |

Никаких ФИО, телефонов, школ. Ученик = `user_id` из MAX + код класса + номер в классе. Сопоставление номера с фамилией — у учителя, вне системы.

## 2. Сценарии по шагам

Формат: **Бот:** текст → [кнопки] → что сохраняем. Тексты — черновые, финальные будут в `product/texts.md`.

### 2.1 Онбординг ученика

**Шаг 1. `/start` (или событие «бот запущен» — MAX API: проверить, есть ли `bot_started`)**

Если пользователь уже зарегистрирован: «Ты ученик класса K7F2, номер 7. Заданий сделано: 5.» → [Продолжить] [Начать заново]. «Начать заново» = `/reset`. Повторный `/start` никогда не создает вторую регистрацию.

Для нового пользователя —
Бот: «Привет. Я даю одно короткое задание в день — на 2–3 минуты. Ты сам выбираешь, какое решать. Через пару недель покажу, к чему ты на самом деле тянешься и что у тебя получается. Это не тест и не оценка. Имя не спрашиваю, оценки никуда не идут.»
→ [Я ученик] [Я учитель]
→ создаем `users` запись с `role = null`, `state = choose_role`

**Шаг 2. Ученик: есть ли код класса**

Бот: «У тебя есть код класса от учителя?»
→ [Есть код] [Нет, сам по себе]

**Шаг 2а. Есть код**

Бот: «Введи код класса (например, `K7F2`)»
→ ждем текст. Проверяем: код существует. Если нет — «Такого кода нет. Проверь, может, перепутана буква. Или нажми [Нет кода]».
Бот: «Теперь твой номер в классе (учитель выдал)»
→ ждем число 1..N. Проверяем: номер в диапазоне и не занят. Если занят — «Этот номер уже занят. Уточни у учителя».
Бот: «Ты — номер 7 в классе K7F2?» → [Да] [Нет, другой]. «Нет» — возвращаемся к вводу номера.
→ `users.role = student`, `class_id`, `number_in_class`, `grade` берем из класса

**Шаг 2б. Нет кода**

Бот: «В каком ты классе?»
→ [7] [8] [9] [10] [11] [Другое]
→ `users.role = student`, `class_id = null`, `grade`

**Шаг 3. Согласие и старт**

Бот: «Как это работает: каждый день в 16:00 я пришлю три карточки с заданиями разного типа. Выбираешь одну, решаешь, я говорю, как получилось. Все. Можно попросить задание и раньше — команда /task.
Продолжая, ты соглашаешься, что бот хранит твои ответы без имени и без школы — только номер в классе. Начнем с первого прямо сейчас?»
→ [Понятно, начнем]
(строка согласия — по требованию про политику обработки данных с вебинара 17.09)
→ `state = idle`, сразу переходим к 2.3

### 2.2 Онбординг учителя

**Шаг 1.** После [Я учитель]:
Бот: «Введите код учителя» → ждем текст, сравниваем с `TEACHER_CODE` из `.env`. Не совпал — «Не тот код. Если вы ученик — нажмите [Я ученик]». Код сообщаем учителям лично; ученик, нажавший «Я учитель» в шутку, дальше не проходит и класс не создает.
Бот: «Создам для вас класс. Какой класс?» → [7] [8] [9] [10] [11]
Бот: «Сколько учеников?» → ждем число 1..40
Бот: «Готово. Код класса: `K7F2`. Номера: 1–27. Раздайте ученикам код и по номеру каждому, у себя запишите, кто под каким номером. Мы фамилии не храним. Отчет по классу — команда /report.»
→ `classes` запись, `users.role = teacher`, `teacher_id`
Учитель может создать несколько классов: /class повторяет шаги.

### 2.3 Задание дня (ядро продукта)

**Шаг 1. Выдача карточек**

Триггер: планировщик в 16:00 по МСК для всех учеников с `state = idle`, или команда /task, или [Давай] из онбординга.

Бот: «Задание дня. Выбери одно:»
→ три кнопки, каждая — карточка одного типа. Текст кнопки — короткий заголовок карточки без указания типа, например: [Цепочка чисел] [Разговор с другом] [Что не так на схеме]
→ пишем `events`: `type = shown`, три `task_id`
→ `state = choosing`

Правило подбора трех карточек: три разных типа из пяти; типы выбираем так, чтобы за последние 5 показов каждый тип был показан примерно одинаково (round-robin по счетчику показов у пользователя). Задание — не показанное этому ученику ранее. Если задания одного типа закончились — берем тип с наименьшим числом показов из оставшихся.

Ограничение: не больше 3 заданий в день на ученика (для пилота — чтобы данные копились быстрее; в проде будет 1). Четвертый /task → «На сегодня хватит, завтра пришлю новые».

**Шаг 2. Выбор**

Ученик нажимает карточку.
→ `events`: `type = chosen`, `task_id`, `latency_ms` от показа до выбора
Бот: полный текст задания + варианты ответа кнопками [А] [Б] [В] [Г]
→ `state = solving`

Если ученик пишет текст вместо кнопки — «Выбери вариант кнопкой ниже». Если нажал старую кнопку от прошлого задания — «Это задание уже закрыто. Текущее — выше» (MAX API: проверить, что callback-кнопки несут payload, по которому отличаем задание).

**Шаг 3. Ответ**

Ученик нажимает вариант.
→ `events`: `type = answered`, `task_id`, `answer`, `is_correct` (для проверяемых), `solve_ms`

Бот отвечает строкой `feedback[answer]` — у каждого варианта свой текст.

Для проверяемого задания (`checkable = true`): верный вариант — «Верно. [почему]», каждый неверный — «Не совсем. [где именно ошибка]. Правильный — Б». Ученик видит не просто «нет», а что конкретно не сошлось.

Для непроверяемого (`checkable = false`, например про людей): «Записал. Тут нет правильного ответа — важно, что ты выбрал. [комментарий именно к этому варианту]».

**Шаг 4. Штрих к профилю**

Бот: «+1 к «[название оси человеческим языком]». Всего заданий: 7. Профиль — /profile. Завтра в 16:00 пришлю новые.»
→ `state = idle`

### 2.4 Профиль ученика — /profile

Меньше 3 выполненных заданий:
Бот: «Пока рано — сделано 1 из 3, нужных для первого наброска. Еще пара заданий.»

3 или 4 выполненных (черновик, v0.8): тот же блок профиля, что ниже, но заголовок «Черновик профиля (по 3 заданиям)» и вместо резюме и направлений — строка «Это набросок по трем заданиям. После пяти будет точнее, это всего два задания завтра». Зачем: лимит 3 в день, и без черновика ребенок в первый день не видит ничего, а без результата в первый день второго дня не будет. После третьего задания в день бот показывает черновик сам, без команды /profile.

5 и больше:
Бот:
```
Твой профиль (по 12 заданиям)

Люди        ████████░░  0.8
Техника     ████░░░░░░  0.4
Знаки       ███████░░░  0.7
Образы      ███░░░░░░░  0.3
Природа     ██░░░░░░░░  0.2

Ты чаще выбираешь задания про людей и знаки — и они у тебя получаются. 
Это про профессии, где надо разбираться в людях и в правилах: 
[3 направления из справочника]

Это не приговор и не тест. Чем больше заданий, тем точнее картина.
```
Пороги и формулы — раздел 4.

### 2.5 Отчет учителя — /report

Бот: «Класс K7F2 (8 класс, 27 учеников). Привязаны: 1–3, 5–8, 10–27. Свободны: 4, 9.
Активных: 22. Прошли 10+ заданий: 15.
Не начинали: 15, 21, 26.
Средний профиль класса: Люди 0.6 · Техника 0.5 · Знаки 0.5 · Образы 0.4 · Природа 0.3
Ученики с выраженным профилем: 11 (см. /report_detail)»

Определения (v0.8): **активный** — привязан к классу и есть `answered` не старше 14 дней (константа `ACTIVE_DAYS`); **не начинали** — привязан, `answered` нет вообще; **прошли 10+** — `answered` ≥ 10 за все время; **средний профиль класса** — только по ученикам с `answered` ≥ 5.

/report_detail → список: «№7 — Люди/Знаки, 14 заданий», «№12 — Техника, 9 заданий»… только номера.

### 2.6 Служебные команды

- `/help` — что умеет бот, команды
- `/task` — задание сейчас (с ограничением 3/день)
- `/profile` — профиль
- `/class` — учителю: создать еще класс
- `/report`, `/report_detail` — учителю
- `/reset` — любому: сбросить роль и привязку, начать с выбора роли. Спрашиваем подтверждение. Ученику удаляем события; учителю классы не трогаем — они остаются за его аккаунтом
- `/number` — ученику: сменить номер в классе. Спрашиваем новый номер; принимаем, если он в диапазоне и свободен. События остаются с учеником
- `/free N` — учителю: освободить номер N в своем классе. Ученик, который был на нем, получает: «Учитель освободил твой номер. Введи свой: /number». Его события не удаляются

Любой неизвестный текст в состоянии `idle`: «Не понял. Команды: /task /profile /help». Бот никогда не молчит в ответ на сообщение.

### 2.6а Ошибки пользователя — валидация и исправление

**Слой 1. Валидация: ошибка не записывается.** Каждое состояние принимает ровно один тип ввода. Все остальное — подсказка, состояние не меняется, бот не падает и не молчит:

| Ввод | Ответ бота |
|---|---|
| Текст там, где ждем число | «Нужно число, например 7» |
| Число вне диапазона | «В классе номера от 1 до 27» |
| Несуществующий код класса | «Такого кода нет. Проверь, может, перепутана буква» |
| Занятый номер | «Этот номер уже занят. Уточни у учителя» |
| Текст там, где ждем кнопку | «Выбери вариант кнопкой ниже» |
| Старая кнопка от прошлого сообщения | «Это задание уже закрыто. Текущее — выше» |
| Неизвестная команда или текст в `idle` | «Не понял. Команды: /task /profile /help» |
| `/start` у зарегистрированного | статус + [Продолжить] [Начать заново] |

**Слой 2. Исправление: ошибка записалась, пользователь чинит сам.** Принцип: одна команда, без админа, без потери данных. Опора — **события принадлежат `users.id` (аккаунту MAX), а не паре «класс + номер»**. Номер — ярлык для учителя; перепривязка меняет ярлык, ни одна строка событий не двигается.

| Ситуация | Как ловим | Как чиним |
|---|---|---|
| Ученик в шутку нажал «Я учитель» | код учителя — не проходит дальше, класс не создается | нажимает [Я ученик] |
| Учитель по ошибке нажал «Я ученик» | сам замечает | `/reset` → выбирает роль заново; классы за аккаунтом остаются |
| Ввел соседний номер, свой свободен | подтверждение «Ты номер 7?» отсекает часть; остальное — настоящий владелец получает «занят» и говорит учителю | сам: `/number`; или учитель: `/free 8` → ученик получает «Учитель освободил твой номер. Введи свой: /number» |
| Ввел соседний номер, он занят | валидация | вводит заново |
| Вася вписал номер Пети, Петя — Васи | никто не получает ошибку; всплывает через детей или через отчет учителя | учитель: `/free 7`, `/free 12` → оба вводят свои через `/number`; события у каждого свои, ничего не переносится |
| Ввел чужой код класса (4 символа из ~30 знаков, ~800 тыс. кодов — опечаткой не попасть) | сам замечает по названию класса в статусе | `/reset` |

Честное ограничение: **автоматически понять, что за номером не тот ребенок, мы не можем** — имен нет, это цена обезличенности. Обнаружение — на учителе и на детях. Поэтому `/report` показывает привязанные и свободные номера, чтобы учитель сверял со своим списком.

**Механика `/free N`:** только в классе этого учителя; `users.number_in_class = NULL` у бывшего владельца, ему отправляется сообщение; при его следующем действии бот сначала просит номер, потом продолжает с того места, где он был. События не трогаются.

**Что сознательно не делаем:** подтверждение смены номера через учителя, историю привязок, автоматический поиск дублей, удаление классов, перехват занятого номера.

## 3. Модель данных (SQLite)

```
users
  id              INTEGER PK
  max_user_id     TEXT UNIQUE      -- id из MAX
  role            TEXT             -- student | teacher | null
  state           TEXT             -- choose_role | enter_code | enter_number | choose_grade | idle | choosing | solving | ...
  grade           INTEGER          -- 7..11, null
  class_id        INTEGER FK       -- null для «сам по себе»
  number_in_class INTEGER
  created_at      DATETIME
  tz_offset       INTEGER          -- на будущее; в MVP всем МСК

classes
  id              INTEGER PK
  code            TEXT UNIQUE      -- 4 символа, без похожих букв (0/O, 1/I)
  grade           INTEGER
  size            INTEGER
  teacher_id      INTEGER FK users
  created_at      DATETIME

tasks                              -- загружается из tasks.json при старте
  id              TEXT PK          -- например L-014
  axis            TEXT             -- H | T | S | I | N (см. раздел 4)
  title           TEXT             -- заголовок на кнопке
  body            TEXT             -- текст задания
  options         JSON             -- ["...", "...", "...", "..."]
  correct         INTEGER          -- индекс, null если непроверяемое
  checkable       BOOLEAN
  feedback        JSON             -- 4 строки, по одной на вариант: что сказать после выбора
  difficulty      INTEGER          -- 1..3

events
  id              INTEGER PK
  user_id         INTEGER FK
  type            TEXT             -- shown | chosen | answered
  task_id         TEXT             -- для shown — через запятую три id
  answer          INTEGER
  is_correct      BOOLEAN
  latency_ms      INTEGER
  created_at      DATETIME

pending_buttons                    -- какие callback сейчас валидны для пользователя
  user_id         INTEGER
  payload         TEXT
  expires_at      DATETIME
```

Одна таблица `events` — источник всего: профиль, отчет, метрики пилота. Ничего не агрегируем заранее.

## 4. Модель профиля

Пять осей по Климову:

| Код | Ось | Человеческое название в боте | Что за задания |
|---|---|---|---|
| H | человек–человек | Люди | ситуации общения, конфликт, мотивация, объяснить кому-то |
| T | человек–техника | Техника | как работает механизм, что сломалось, порядок сборки |
| S | человек–знак | Знаки | числа, логика, тексты, таблицы, коды, правила |
| I | человек–образ | Образы | композиция, стиль, что выбивается из ряда, придумать |
| N | человек–природа | Природа | живое, наблюдение, эксперимент, причина–следствие в природе |

Для каждой оси `a` по всем событиям пользователя:

```
shown_a   = сколько раз задание типа a было среди трех карточек
chosen_a  = сколько раз выбрал задание типа a
solved_a  = сколько заданий типа a решил (answered)
correct_a = сколько из проверяемых решил верно

preference_a = chosen_a / shown_a            (0..1; если shown_a = 0 → 0)
success_a    = correct_a / checkable_solved_a (0..1; если проверяемых нет → средняя успешность ученика по остальным осям)

score_a = preference_a * (0.6 + 0.4 * success_a)
```

Успешность не добавляется к склонности, а корректирует ее: верные ответы оставляют оценку равной склонности, неверные снижают до 0.6 от нее.

Если по оси нет проверяемых заданий, вместо неизвестной успешности берется средняя успешность ученика по тем осям, где проверка была. Это правка от 25.09: раньше в таком случае множитель равнялся единице. Ось «Люди» непроверяема целиком — в банке нет ни одного задания с правильным ответом — и потому всегда получала максимальный множитель, тогда как остальные оси теряли на каждой ошибке. На синтетике с равной склонностью «Люди» выходили в среднем на 17% выше самой низкой оси и становились ведущими у 24% ровных учеников вместо ожидаемых 20%. Это прямо противоречило свойству, ради которого формулу и выбрали (см. ниже). Средний множитель означает «про эту ось мы не знаем, поэтому не даем ни бонуса, ни штрафа»; если проверяемых ответов нет вообще, замещать нечем и множитель остается прежним.

Почему мультипликативно, а не «0.6·склонность + 0.4·успешность» (так было в v0.1–0.4): аддитивная формула при равной склонности давала проверяемым осям до +0.4, и у всех учеников появлялся бы ложный уклон в «Знаки» и «Технику». В новой формуле при равной склонности все оси равны, потолок у всех 1.0. Веса 0.6/0.4 — склонность важнее способности для профориентации; это допущение, на защите так и говорим. Реализация и тесты — `bot/scoring.py`, `bot/tests/test_scoring.py`.

**Различимость профиля** (для метрик пилота и для фразы «выраженный профиль»):
```
distinct = max(score) - mean(остальных четырех)
выраженный профиль: distinct >= 0.30 и solved_total >= 10
```

Порог 0.30 выбран замером на синтетике, где заложенный характер известен заранее (`validate_model.py`, 200 учеников на характер, усреднение по трем прогонам). Что дает порог: доля характерных учеников, которые получат вывод о себе; доля ровных учеников, которым мы ошибочно скажем «профиль выражен»; точность вывода у тех, кому он выдан.

| Порог | Получат вывод | Ошибочно сказали ровному | Точность вывода |
|---|---|---|---|
| 0.25 (было) | 84% | 31% | 89% |
| 0.30 (стало) | 75% | 16% | 91% |
| 0.35 | 61% | 8% | 94% |

При 0.25 почти треть детей с ровным профилем услышала бы «ты явно про Людей» и могла бы на этом что-то решить. Ложный вывод здесь дороже отсутствия вывода: фраза «картина пока ровная» ни к чему не подталкивает. Поэтому осознанно жертвуем девятью процентными пунктами охвата.

**Ведущие оси** — одна или две с наибольшим score, если вторая отстает от первой не больше чем на 0.1.

**Подборка направлений** — справочник `data/directions.json` (33 записи: 4 профиля 10 класса и 29 специальностей колледжей). Запись:

```json
{ "id": "C-IT", "kind": "college", "title": "Информационные системы и программирование",
  "axes": ["S", "T"], "hint": "Писать код, собирать приложения, разбираться в данных." }
```

`kind` — `profile10` или `college`; `axes` — одна или две оси, первая главная; `hint` — одна строка для мини-аппа и отчета, в сообщении бота показываем только `title`.

Правило (реализовано в `scoring.pick_directions`, тесты в `tests/test_scoring.py`): ранг записи = +4, если ее главная ось совпадает с первой ведущей осью ученика; +2, если главная ось есть среди ведущих, но не первая; +1, если вторая ось записи есть среди ведущих. Ранг 0 — не показываем. Берем до 3: сначала лучший профиль 10 класса, затем лучшую специальность колледжа, затем лучшие из оставшихся. Среди равных по рангу — порядок из файла со сдвигом на внутренний id ученика (`salt`), чтобы одноклассники с одинаковым профилем видели разные подборки. Если ведущих осей нет (плоский профиль) — `profile.directions.none`.

Названия специальностей даны по перечню СПО в упрощенном виде, без кодов; коды добавим на масштабировании, когда справочник вырастет до полного перечня региона.

**Что не делаем:** нормировку на популяцию, весовые коэффициенты по сложности, временной спад. Все это — «переменная часть» для масштабирования, и это честно написать.

## 7. Что решить до начала кода (до 17.09)

1. Название и ник бота — Вектор, @vector_bot. Закрыто 17.09.
2. Кто создает бота и получает токен — один человек, токен в .env у каждого. Там же `TEACHER_CODE`.
3. Polling или webhook — **оба режима, переключатель `MODE` в `.env`**: polling для локальной разработки, webhook на сервере. Команда MAX на вебинаре 17.09: long polling уходит, для прода — webhook. Бот должен быть онлайн с 30.09 по 14.10 на нашем хостинге (облако с публичным HTTPS).
4. Библиотека: кандидат https://github.com/love-apples/maxapi. Даниил тратит час на hello world с ней; если чисто — берем (проверить лицензию), если странности — своя обертка на `httpx`. ORM не используем, слой доступа к данным — обычные функции (решение Карима).
5. Дедлайн онлайн-этапа — **30.09 в 12:00**, загружает капитан (Карим) через ЛК. Загружаем 29.09 днем. Заморозка кода — 26.09 вечер.
6. Сдается бот, созданный на токене организаторов, с их ником. `@vector_bot` на своем токене — только для разработки. Переименовать бота смогут только финалисты.
